DS101 Data Systems - Coursework 1: The Riverside Community Library Loans Database

Quillmere Institute is a fictional institution. This material was written for the CourseFlow retrieval benchmark and describes no real course.

Overview

Coursework 1 asks you to design and partly implement the database behind the loans desk of the Riverside Community Library, a small lending library run by volunteers. The library currently keeps its records in a single shared spreadsheet with one row per loan. Each row repeats the member's name, postal address and telephone number, the title, author and shelf mark of the item, and the dates on which the item was borrowed, due back and returned. Volunteers have reported that addresses are out of date in some rows but not in others, that some items appear twice with slightly different titles, and that nobody can say with confidence how many items are on loan at any moment.

Your task is to replace the spreadsheet with a relational design that removes these problems, to implement that design in PostgreSQL, and to show that it answers the questions the volunteers care about. The coursework draws on the lectures on the relational model, entity-relationship modelling and normalisation, and on the first two labs.

Coursework 1 is worth 40 percent of the module mark. The remaining 60 percent comes from the written examination in January.

Submission

Submit Coursework 1 through the module's coursework portal by 14:00 (UK time) on Friday 6 November 2026.

Coursework 1 may be completed in groups of up to three students, with one submission per group and a short statement of each member's contribution.

The submission is a single PDF report together with one SQL script. Name the script with your group number, for example group07_schema.sql. The script must run without errors on a fresh PostgreSQL 16 database, because the markers will run it exactly as submitted.

The report has a limit of 2,000 words, excluding the diagrams, tables, the SQL listings in the appendix and the reference list. Text beyond the limit will not be read.

What you must produce

  1. An entity-relationship diagram of the library's loans domain in crow's-foot notation, showing every entity, its attributes, its primary key and the cardinality and optionality of every relationship.
  2. A relational schema derived from the diagram, with every primary key, foreign key, NOT NULL and CHECK constraint written out.
  3. A normalisation analysis that starts from the spreadsheet as a single relation, lists the functional dependencies you identified, and decomposes the relation step by step. Explain why your final schema is in third normal form.
  4. An SQL script that creates the schema, inserts a small set of realistic test data (at least ten members, twenty items and thirty loans) and runs the five queries listed below.
  5. A short reflection on one design decision you would revisit if the library grew to several branches.

The five queries

Your script must include one query for each of the following questions. Each query must be preceded by a comment that restates the question it answers.

  1. Which items are currently on loan, and to whom?
  2. Which loans are overdue today, ordered by the number of days overdue, longest first?
  3. How many loans has each member made in the current calendar year, including members who have made none?
  4. Which authors have more than three different titles in the collection?
  5. Which items have never been borrowed?

Queries that return the correct rows for the test data but would return wrong rows for other reasonable data, for example because they compare dates as text, will lose marks.

Generative AI tools must not be used for any part of this coursework. Diagramming tools, spell checkers and the PostgreSQL documentation may be used freely.

Advice

Start from the questions the volunteers ask rather than from the spreadsheet columns. A design that stores every fact once is easier to keep correct, but you still need to be able to answer each of the five questions with a query that a volunteer could understand when it is explained to them.

Keep the diagram and the schema in step. Markers check that every entity in the diagram appears as a table, that every relationship appears as a foreign key or a linking table, and that nothing appears in the schema that the diagram does not explain. If you change one, change the other in the same sitting.

Write the test data so that it exercises the awkward cases: a member with no loans, an item that has never been borrowed, a loan returned on its due date, a loan returned late, and an item borrowed more than once by the same member. Data that only contains tidy cases will not reveal a wrong query.

  • LO3: use functional dependencies to evaluate and improve a schema.
  • LO4: write correct SQL queries for realistic information needs.
