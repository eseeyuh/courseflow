What a document store is

A document store keeps data as self-contained documents, usually in a JSON-like format, grouped into collections. A document can contain nested objects and arrays, so a single document can hold an order together with all of its order lines, or a customer together with a list of delivery addresses. There is no fixed schema at the level of the collection: two documents in the same collection may have different fields.

The appeal is that the shape of the stored data can match the shape of the objects in the application. Reading an order with its lines is one lookup by key, with no joins, and the result arrives already assembled. For applications whose main access pattern is fetching and saving whole aggregates by their identifier, this is both simple and fast.

Embedding versus referencing

The central design decision in a document store is whether related data is embedded in a document or referenced by an identifier. Embedding puts the related data inside the parent document. Referencing stores only the identifier of another document, which the application must then fetch separately, because most document stores offer limited or no joins.

Embedding works well when the related data belongs to the parent and is read with it: the lines of an order, the steps of a recipe. It works poorly when the related data is shared by many parents or changes independently of them. An author embedded in every book document must be updated in every book when the author's details change.

Copying a customer's address into every order document means a change of address must be applied to many documents, a cost that document stores accept in exchange for reading an order without joins. Sometimes this is exactly right. The address on an order should be the address the order was delivered to, which must not change when the customer moves; copying it into the order records a historical fact rather than duplicating a current one.

Denormalisation as a deliberate choice

Relational designers denormalise too, but they treat it as an optimisation with a cost. A reporting table that stores each member's total number of loans avoids recomputing the total for every report, at the price of keeping the stored total in step with the loans table. If something updates loans without updating the total, the report is wrong and nothing warns you.

The difference between the two worlds is the default. A relational design starts normalised and adds redundancy where measurements justify it, with a mechanism, such as a trigger or a scheduled rebuild, that keeps each copy correct. A document design starts from the access patterns and embeds by default, accepting redundancy, and has to think carefully about every piece of data that is shared or that changes.

Consistency in distributed stores

Many document stores are designed to run on several machines, with each document stored on more than one of them. Keeping the copies in step costs coordination between machines, and when the network between them fails, a system must choose between refusing some requests and answering with data that may be out of date. Systems that choose availability offer eventual consistency: if no new writes arrive, all copies will eventually agree, but a read straight after a write may return the old value.

This is a different use of the word consistency from the C in ACID. ACID consistency means that a transaction preserves the declared integrity constraints. Replica consistency means that copies of the same data on different machines agree. A system can offer one without the other, and confusing the two is a common source of misunderstanding in design discussions.

Modern document stores increasingly offer multi-document transactions and configurable read and write guarantees, narrowing the gap with relational systems. The trade-off has not disappeared, though: the stronger the guarantee requested, the more coordination each operation needs, and the more latency it adds.

Indexes in document stores

Document stores index fields inside documents, including fields of nested objects and the elements of arrays. A secondary index on a field such as customer.city lets queries find documents by that field without scanning the collection, with the same trade-off as in a relational system: faster reads, slower writes and more storage. Compound indexes follow the same left-to-right rules as composite B-tree indexes, because many document stores use B-trees underneath.

When to choose which

A relational database is the safer default when the data is shared between many parts of an application, when integrity rules matter, and when questions about the data are not all known in advance. A document store fits when the application reads and writes self-contained aggregates by key, when the structure of those aggregates varies, and when the team accepts responsibility for keeping duplicated data correct in application code.

Many systems use both: a relational database as the system of record, and a document store or search index fed from it for particular read-heavy features. The rule from Lecture 3 still applies in such systems. Know where every copy of each fact lives, why it is there, and what keeps it correct.
